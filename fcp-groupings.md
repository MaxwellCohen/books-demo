## Summary

The First Contentful Paint (FCP) values in this project do not form a smooth curve. They cluster into four bands:

| Band | Roughly | Critical-path shape |
| --- | --- | --- |
| Fast | **0.9–1.0s** | One request: the HTML already contains everything needed to paint |
| Middle | **1.1–1.5s** | Two serialized requests: HTML plus one asset or render step |
| Slow-middle | **1.7–2.0s** | Three serialized requests, or a cold cache / cold worker |
| Baseline | **2.4–2.8s** | Four or more serialized requests, including a cross-origin font |

The bands are not a framework ranking. They are a count of **how many network round-trips must finish, one after another, before the first pixel can be painted.** On mobile Lighthouse (simulated Slow 4G plus a 4× CPU throttle), each hop costs roughly 0.4–0.6 seconds. Remove one hop and the app moves down a whole band.

The clearest evidence in this repository is that the band is not stable per app or per framework:

- `next-books` measures **0.9s on Vercel and Netlify and 1.0s on Cloudflare** in the 9/16 run, and **0.9s on all three** in the 9/22 run. It is effectively host-invariant because there is no second origin or second request on its critical path.
- In the 9/17 "basic cache" run, the **same Waku build** measured **0.9s on Vercel, 1.7s on Netlify, and 2.6s on Cloudflare**. Same code, three different bands.

That second result is the key. A framework cannot explain a 1.7-second spread within one build. Cache state and the number of serialized requests can.

## Why the result is bands instead of a curve

FCP is not a measure of "how much work the app did." It is a milestone on a dependency chain. A browser cannot paint text until it has:

1. the HTML document,
2. a stylesheet that applies to that text (unless the CSS is inlined),
3. a font that can render that text (unless the font is a system font or already present),
4. and, for client-rendered content, the JavaScript that produces the DOM.

Each of those can depend on the previous one. That is a **critical request chain**. If the HTML links a stylesheet, the browser must fetch the stylesheet before it can paint. If that stylesheet imports a font, the font fetch starts only after the stylesheet finishes. Each link is a full round-trip.

There are three reasons this produces visible steps rather than a gradient:

1. **A round-trip is a fixed cost, not a slope.** Lighthouse's mobile profile applies high latency and low bandwidth. A request that would take 20ms on a desk connection takes hundreds of milliseconds under that profile. Cutting a request in half does not help; removing it does.
2. **Caching is close to binary.** A warm edge cache returns the HTML immediately. A cold cache runs the server, reads the database, and renders. That is one or two extra hops, not a small percentage.
3. **A cross-origin font is two hops.** Google Fonts is not one request. The page fetches the CSS from `fonts.googleapis.com`, and then the font file from `fonts.gstatic.com`. Two new origins means DNS, TLS, and two serialized requests before text can use the font. That is why the baseline band is so tight around 2.5s.

This is also why half-optimizing does not produce a half-band. Removing the font CDN but leaving a render-blocking stylesheet leaves one hop. Inlining the CSS but keeping the font CDN leaves two. You only change bands when you remove a link from the chain.

## Band-by-band anatomy

### 0.9–1.0s: the HTML is the only request

Everything required for first paint is already in the first response:

- CSS is inlined in a `<style>` tag, so there is no render-blocking stylesheet request.
- The font is self-hosted and, ideally, preloaded, so the font file is requested in parallel with HTML parsing rather than chained behind a stylesheet on a third-party origin.
- The data needed for the shell is cached, so the server does not wait on a database query before sending the first byte.

In this repository, Next is the canonical example. `next-books/next.config.ts` enables `inlineCss`, and `next/font` self-hosts and preloads the font. The catalog queries are marked `'use cache'` with `cacheLife('hours')`. The result is 0.9s on all three hosts.

The `nuxt-books-optimized-max` build reaches the same band on Netlify (0.9s) because it adds `features.inlineStyles` and a persistent Nitro cache. The fast band is not exclusive to Next; it is exclusive to apps that have collapsed the chain to one request.

### 1.1–1.5s: one link remains

Most optimized Vite-based ports land here. They removed the worst offender (the cross-origin font) and added HTTP caching, but one serialized request is still on the path. Usually that is one of:

- an external stylesheet that still has to be fetched before paint,
- a font file that is self-hosted but not preloaded, so it is discovered late,
- or a server render that is fast but not served from a warm static/edge cache.

The code differences are visible in the repository:

- `svelte-books/vite.config.ts` sets `inlineStyleThreshold: Number.POSITIVE_INFINITY`, which inlines the page CSS, and `svelte-books/src/routes/layout.css` imports `@fontsource-variable/geist`. Svelte measures 1.4–1.5s.
- `solid-books/src/Document.tsx` imports `./app.css?inline` and the woff2 URL directly, emits `<style>{appCss}</style>`, and preloads the font. Solid measures 1.1–1.5s.
- `pracht-books/vite.config.ts` uses `inlineCss: true` and a `@fontsource-variable/geist` import. Pracht measures 1.2–1.5s.
- `waku-books` on its optimized branch gets the same treatment and lands at 1.4s.

The band is about one missing link, not about framework weight.

### 1.7–2.0s: two links remain, or the cache is cold

In the 9/22 data, this band is almost entirely **Cloudflare Workers** builds: Solid 1.7, Nuxt 1.7, Ember 1.8. In the 9/17 run it also contains cold-cache measurements of otherwise-fast apps: Svelte on Vercel 1.7, Solid on Netlify 1.7, Waku on Netlify 1.7.

Two mechanisms put an app here:

1. **No warm HTML cache.** Vercel and Netlify can serve a cached document immediately. A Cloudflare Worker often runs the request path: cold start, render, cache lookup. That is an extra serialized step even when the data cache hits.
2. **A cache miss on the measurement run.** If the run arrives before the page or its assets are warm, the app pays the render and the asset fetch. The same code may measure 1.2s five minutes later.

This is the "almost there" band. It is usually a caching/deployment problem, not a code problem. The fix is to make the cache persistent and the HTML warm, not to rewrite components.

### 2.4–2.8s: the full baseline waterfall

Every baseline `main` build lands here, on every host, in every framework. The chain is typically:

```text
HTML (waits on a database query)
  -> render-blocking CSS bundle
    -> Google Fonts CSS from fonts.googleapis.com
      -> woff2 from fonts.gstatic.com
```

Four serialized hops, one of them cross-origin. `waku-books/src/pages/_layout.tsx` is a clean example: it preconnects to both Google origins and then loads the stylesheet with `display=block`. Preconnect hides DNS and TLS setup, but it does not remove the two requests or their order relative to paint.

The uniformity of this band across frameworks is the point. The slow apps are not slow because Svelte or Solid is slow. They are slow because the same four-hop loading strategy was reproduced in each port.

## Why the "basic cache" run spans every band

The 9/17 run is worth understanding because it looks contradictory: one build, three hosts, 0.9s to 2.6s.

That is what a partially cached app looks like. If the HTML, the JS/CSS, the font, and the data are all warm, the app paints after one request. If one of them is cold, it adds a hop. If the measurement lands on a cold server or a cold worker, it adds another. The build did not change; the state of the caches did.

This is a measurement lesson as much as a performance lesson: a single Lighthouse run is a sample, not a property of the app. To compare builds, run each several times and look at the critical path, not just the summary number.

## How to move an app down a band

Do these in order. Each one removes roughly one serialized request.

### 1. Remove the cross-origin font request

This is the biggest single lever, worth about 1–1.5 seconds on these tests.

- Replace the Google Fonts `<link>` with a self-hosted font: `@fontsource-variable/geist`, `next/font`, or a woff2 checked into the project.
- Add a preload so the font is discovered with the HTML, not after the CSS:

  ```html
  <link rel="preload" as="font" type="font/woff2" href="/fonts/geist.woff2" crossorigin>
  ```

- Use `font-display: swap` or `optional` so text can paint with a fallback instead of waiting.
- Delete `preconnect` hints to `fonts.googleapis.com` and `fonts.gstatic.com` once the font is local. They no longer do anything useful.

In this repository, `solid-books/src/Document.tsx` is the model: it imports the woff2 URL, preloads it, and inlines the CSS.

### 2. Inline the stylesheet

A separate stylesheet is a render-blocking request. If the CSS is small (single-digit KB gzipped), put it in the HTML:

- **Next:** [`experimental.inlineCss: true`](https://nextjs.org/docs/app/api-reference/config/next-config-js/inlineCss).
- **SvelteKit:** [`inlineStyleThreshold: Number.POSITIVE_INFINITY`](https://svelte.dev/docs/kit/@sveltejs-kit-vite) (or a threshold in bytes).
- **Solid/Vite:** import the CSS with [`?inline`](https://vite.dev/guide/assets#explicit-url-imports) and render a `<style>` tag server-side.
- **Pracht:** [`inlineCss: true`](https://pracht.resynapse.dev/docs/styling).
- **Nuxt:** [`features.inlineStyles: true`](https://nuxt.com/docs/4.x/guide/going-further/features).

If the CSS is large, do not inline it; instead serve it from the same origin and preload it. The goal is the same either way: do not make paint wait on a request that could have been avoided.

### 3. Cache the data so the HTML does not wait on the database

A database query before the first byte is a full server-side hop that no amount of client optimization can hide.

- **Next:** mark the query [`'use cache'`](https://nextjs.org/docs/app/api-reference/directives/use-cache) and give it a [`cacheLife`](https://nextjs.org/docs/app/api-reference/functions/cacheLife).
- **Nuxt:** use `defineCachedEventHandler`, set `nitro.storage.cache`, and add a `routeRules` cache rule ([Nitro cache docs](https://nitro.build/docs/cache)).
- **SvelteKit / SolidStart / others:** put a cache layer in front of the query — [Vercel Runtime Cache](https://vercel.com/docs/caching/runtime-cache), [Netlify Blobs](https://docs.netlify.com/blobs/overview/), or the [Cloudflare Cache API](https://developers.cloudflare.com/workers/runtime-apis/cache/). `svelte-books/src/lib/server/catalog-cache.ts` is a host-aware implementation of exactly this.

On Cloudflare, make the cache **persistent**. In-memory caches do not survive between isolates, which is why a cache that works on Vercel can silently miss on Workers.

### 4. Make the HTML warm at the edge

Even with cached data, a Worker that renders on every request pays a render hop. Use one of:

- static generation where the page allows it,
- ISR / stale-while-revalidate,
- Cloudflare's Cache API (`caches.default`) or KV for the rendered document,
- Nitro's persistent cache driver for the host.

This is the specific change that separates the 1.1–1.5 band from the 1.7–2.0 band in the Cloudflare results.

### 5. Server-render the shell; do not let JavaScript gate first paint

If the first meaningful markup is produced by client-side JavaScript, FCP waits on the JS bundle: download, parse, execute, then render. Render the shell on the server and stream the slow parts behind boundaries (Suspense in React, or the framework equivalent). Keep the shell static so it can paint immediately.

### 6. Measure the critical path, not the score

To find out which band an app is in and why:

1. Open Lighthouse's **critical request chain**, or the DevTools Performance panel filtered to the FCP timestamp.
2. List every request that must complete before FCP.
3. Count the serialized links. That count is the band.
4. Remove one link. Re-measure. Repeat.

Useful checks while doing this:

- Is there any request to `fonts.googleapis.com` or `fonts.gstatic.com`? That is two hops.
- Is the main stylesheet a separate request? That is one hop.
- Does the HTML response time spike on a cold cache? That is a server hop.
- On Cloudflare, is the document actually served from cache, or re-rendered?

## Caveats

- **Lab vs field.** These are mobile Lighthouse lab results, not real-user data. They measure a cold, throttled first load. Real users on warm caches, fast connections, or repeat visits will see different numbers.
- **First load only.** Much of what makes the fast apps feel fast — prefetching, navigation on pointer-down, keeping the catalog in memory — does not show up in FCP. A slow FCP is not the same as a slow app, and a fast FCP is not the same as a fast app.
- **Run-to-run noise is large.** The 9/17 run demonstrates this. Compare medians of several runs, not single samples.
- **Inlining has a trade-off.** Inlined CSS is not cached separately, so it is re-downloaded with every HTML response. It is a good trade for small stylesheets and a bad one for large ones.
- **Host differences are real but small once the chain is collapsed.** The 9/22 optimized results still show a ~0.5s spread across hosts, mostly from cache behavior and cold starts. That is a smaller effect than the 1.5s gap between baseline and optimized.

## The one-sentence version

FCP is quantized by the number of serialized requests on the critical path; self-host and preload the font, inline the CSS, cache the data and the HTML, and render the shell on the server — each removal moves the app down a band.
