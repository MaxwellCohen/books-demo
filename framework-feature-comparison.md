How to read it at a glance:

- ✅ **1st-party / built-in** — the framework covers it with a default, a stable flag, or an official module/package from the framework team. Whether it is on by default or added as a plugin does not matter: `@nuxt/image`, `@sveltejs/enhanced-img`, and `next/image` all count the same.
- 🧪 **Experimental / third-party** — the only path is a first-party API marked experimental or unstable, or a community package maintained outside the framework team.
- 🔧 **Manual** — no first-party or third-party package covers it; the app (or this repo) wires it by hand, or goes without.

**Scoring:** ✅ = 2 points, 🧪 = 1, 🔧 = 0. Each table ends with a score row.

The labels describe **framework capability**, not what a particular port chose. Opt-in is not a penalty: a framework that ships a capability as an official module scores the same as one that turns it on by default. Several ports took a manual route even where a first-party primitive existed; the feature sections below call that out and link the setup docs for each framework.

## Summary

**Next is the only framework that uses all five levers in this benchmark.** Four ship as defaults or first-party components; CSS inlining needs one flag, and that flag is still `experimental`. Nuxt and Pracht have first-party support for all five as well — mostly as official modules or per-route options rather than defaults — so they score higher on capability. Nuxt-max uses most of them and matches Next's 0.9s; this Pracht port chose manual alternatives for fonts and caching. The Vite-based ports are missing at least one lever and generally reach the middle FCP band rather than 0.9s.

That is a claim about first paint, not about overall breadth. Next trails several of these frameworks on islands, per-route render policy, and deploy adapters; the [second table](#other-performance-features) covers those.

| Framework | What it ships | What this port added or chose | Best measured FCP |
| --- | --- | --- | --- |
| Next | All five, as flags/defaults | Nothing | 0.9s |
| Nuxt (max) | Inline styles flag, official font/image modules, cache, prefetch | Enabled inline styles; chose Fontsource over `@nuxt/fonts` | 0.9s (9/22) |
| SvelteKit | Inline-CSS and prefetch flags, `enhanced-img` module | Fonts, server cache; used Unpic/IPX instead of `enhanced-img` | 1.4–1.5s |
| SolidStart | Router `usePreloadRoute` only | CSS inline, fonts, images; cache still missing | 1.1–1.7s |
| TanStack Start | Router prefetch, ISR, static prerender | CSS inline, fonts, images | not in the 9/xx runs |
| Pracht | Inline CSS, `defineFont`, image module, ISG, prefetch | Used Fontsource and a manual catalog cache | 1.2–1.5s |
| Waku | Still-unstable prefetch helpers; separate `waku-cache` package | Fonts, cache; no CSS inline or images | 1.4s optimized / 2.4–2.6s baseline |

The pattern matches the band model: the 0.9s samples have all five levers and a warm cache; the middle band removed the font and data hops but left one request; the baseline band has the full waterfall. The framework label is a proxy for how many of these five features ship in the box — not for how fast the runtime is.

## Feature summaries

### 1. Production CSS inlining

**Summary:** Nuxt, SvelteKit, and Pracht expose a stable build flag that inlines the stylesheet; Next's flag is under `experimental`. SolidStart and TanStack Start have no build flag but can import the CSS with `?inline` by hand. Waku and Ember still link a render-blocking stylesheet.

- **Next** — [`experimental.inlineCss: true`](https://nextjs.org/docs/app/api-reference/config/next-config-js/inlineCss) in `next.config.ts`. One flag, but still under the `experimental` key — hence 🧪. It is the main reason Next's first paint is under a second.
- **Nuxt** — [`features.inlineStyles: true`](https://nuxt.com/docs/4.x/guide/going-further/features), but only on the `nuxt-books-optimized-max` branch. The plain `optimized` build leaves the stylesheet linked and measures 1.2s+; the max build reaches 0.9s.
- **SvelteKit** — [`inlineStyleThreshold: Number.POSITIVE_INFINITY`](https://svelte.dev/docs/kit/@sveltejs-kit-vite) in `vite.config.ts`. One line, but you have to know it exists.
- **SolidStart** — no build flag. `src/Document.tsx` imports `app.css?inline` (a [Vite asset feature](https://vite.dev/guide/assets#explicit-url-imports)) and renders a `<style>` tag. The plugin's `start.css` option only inlines dev CSS for no-FOUC; production still uses built assets.
- **TanStack Start** — no build flag. Both the React and Solid roots import `styles.css?inline` (or `app.css?inline`) and pass `styles: [{ children: appCss }]` in the route `head()` ([CSS styling guide](https://tanstack.com/start/latest/docs/framework/react/guide/css-styling)).
- **Pracht** — [`inlineCss: true`](https://pracht.resynapse.dev/docs/styling) on the `@pracht/vite-plugin` options.
- **Waku** — no support; the HTML links the built stylesheet ([styling docs](https://waku.gg/#styling)).
- **Ember** — no support; `index.html` links `/app/styles/app.css`, and the optimized branch does not change that ([asset compilation](https://cli.emberjs.com/release/advanced-use/asset-compilation/)).

The notable result: inlining is *not* required to leave the 2.5s band. Waku-optimized (1.4s) and Ember-optimized (1.4–1.6s on Vercel/Netlify, 1.8s on Cloudflare) skipped it and still reached the middle band because they removed the font hop. It does look required for the 0.9s samples (Next, and Nuxt-max on 9/22), which also have the data cache warm.

### 2. Font optimization

**Summary:** Next and Pracht have first-party font primitives (`next/font` and `defineFont()`); Nuxt has the official `@nuxt/fonts` module, which counts the same. Every other framework relies on the community `@fontsource` packages (🧪 third-party) for self-hosting, and the app adds any preload itself.

- **Next** — [`next/font/google`](https://nextjs.org/docs/app/api-reference/components/font) self-hosts, subsets, generates the `@font-face`, and preloads at build time. No config beyond using it in the layout.
- **Nuxt** — first-party via the official [`@nuxt/fonts`](https://nuxt.com/modules/fonts) module resolves the fonts used in CSS, downloads them at build time, serves them from your own origin, injects `@font-face` rules, generates fallback metrics for lower CLS, and can subset. This port does not use it — it imports `@fontsource-variable/geist` manually from `app/assets/css/main.css` — so the capability exists in the framework, even though the measured build took the third-party route.
- **SvelteKit** — third-party: `@fontsource-variable/geist` imported in `src/routes/layout.css` ([Fontsource](https://fontsource.org)). No explicit preload link, but the font is discovered from the inlined stylesheet. SvelteKit has no first-party font module.
- **SolidStart** — third-party: `@fontsource-variable/geist` plus an explicit `<link rel="preload" as="font">` with the hashed woff2 URL in `src/Document.tsx` ([static assets](https://docs.solidjs.com/solid-start/v1/building-your-application/static-assets)).
- **TanStack Start** — third-party: [`@fontsource`](https://fontsource.org) in the global stylesheet. The Solid version also preloads the woff2 in `__root.tsx`; the React version relies on the inlined CSS to discover it.
- **Pracht** — first-party: [`defineFont()`](https://pracht.resynapse.dev/docs/fonts) from `@pracht/core` generates typed `@font-face` rules, automatic preload links, and fallback metrics. This port chose `@fontsource-variable/geist` in `src/styles/global.css` instead.
- **Waku** — third-party on `optimized` (fontsource import); `main` still loads Geist from `fonts.googleapis.com` with `display=block`. Waku's docs recommend `@fontsource/*` because there is no `next/font` equivalent ([migration guide](https://waku.gg/guides/migrating-from-nextjs)).
- **Ember** — third-party on `optimized` ([Fontsource](https://fontsource.org) import); `main` uses the same Google Fonts link with `preconnect`. Ember has no first-party font module ([asset compilation](https://cli.emberjs.com/release/advanced-use/asset-compilation/)).

Next, Nuxt (via `@nuxt/fonts`), and Pracht have first-party font support. Next uses it here; the Nuxt and Pracht measured builds use Fontsource instead. Every other framework uses a community package (`@fontsource`) or a CDN. Every optimized port that left the 2.5s band had removed the cross-origin font request, either by importing `@fontsource` or by using a first-party font primitive.

### 3. Image pipeline

**Summary:** Next, Nuxt (`@nuxt/image`), SvelteKit (`@sveltejs/enhanced-img`), and Pracht (`@pracht/image`) all have first-party image components and optimizers. SolidStart and TanStack Start use the third-party Unpic plus a host optimizer, and the same React package would work for Waku. Ember uses plain `<img>` tags.

- **Next** — [`next/image`](https://nextjs.org/docs/app/api-reference/components/image) plus the built-in optimizer, `priority` on the first ten covers, `sizes`, and ThumbHash placeholders.
- **Nuxt** — first-party: the official [`@nuxt/image`](https://nuxt.com/modules/image) module plus `<NuxtImg preload>` on the first covers.
- **SvelteKit** — first-party: the framework offers [`@sveltejs/enhanced-img`](https://svelte.dev/docs/kit/images), but this port uses Unpic transforms plus an `ipx` handler (`src/lib/server/ipx-handler.ts`), disabled on Cloudflare.
- **SolidStart** — third-party: [Unpic](https://unpic.pics) plus the per-host Nitro image config and the cover preload components.
- **TanStack Start** — third-party: [Unpic](https://unpic.pics) URL transforms plus IPX/Nitro or the host CDN, chosen in `vite.config.ts`.
- **Pracht** — first-party [`@pracht/image`](https://pracht.resynapse.dev/docs/images) plus per-host adapters (`@pracht/adapter-vercel`, `-netlify`, `-cloudflare`).
- **Waku** — third-party path available, not used: Unpic's React component works in any React app, but this port only rewrites Goodreads' `m` size token to `l`, emits no `srcset`, and runs no optimizer ([static assets](https://waku.gg/#static-assets)).
- **Ember** — none: a plain `<img>` with no `srcset` or `sizes` ([asset compilation](https://cli.emberjs.com/release/advanced-use/asset-compilation/)).

This item affects LCP more than FCP, which is why the image-poor ports can still be fast at first paint and slow on the cover.

### 4. Data and HTML caching

**Summary:** Next and Nuxt have first-class data/caching models. TanStack Start and Pracht offer ISR/ISG as first-party per-route rendering modes, and Waku documents its separate `waku-cache` package. SvelteKit and Ember have no data cache, so this repo implements host-aware caches. SolidStart has no cache here and still hits Postgres on a cold request.

- **Next** — [`cacheComponents`](https://nextjs.org/docs/app/api-reference/config/next-config-js/cacheComponents), [`'use cache'`](https://nextjs.org/docs/app/api-reference/directives/use-cache), and `cacheLife('hours')` on the catalog queries.
- **Nuxt** — [`defineCachedEventHandler` / `nitro.storage.cache`](https://nitro.build/docs/cache) and a header-only `routeRules` cache; the max branch adds persistent drivers for Vercel, Netlify, and Cloudflare KV.
- **SvelteKit** — manual: `src/lib/server/catalog-cache.ts` with Vercel Cache, Netlify Blobs, and the Workers KV/Cache API paths. SvelteKit's built-in [`prerender`](https://svelte.dev/docs/kit/page-options) covers static routes, but not this dynamic catalog.
- **SolidStart** — manual (none in this port): loaders in `src/features/book/book-queries.ts` query Postgres on a cold request, and there is no component-level cache yet. [Route pre-rendering](https://docs.solidjs.com/solid-start/v1/building-your-application/route-prerendering) exists for static routes only.
- **TanStack Start** — first-party: [`ISR`](https://tanstack.com/start/latest/docs/framework/react/guide/isr) and [static prerendering](https://tanstack.com/start/latest/docs/framework/react/guide/static-prerendering) are built in. This port instead uses `src/lib/catalog-cache.ts` plus document `Cache-Control` headers in `src/start.ts`.
- **Pracht** — first-party: [`ISG`](https://pracht.resynapse.dev/docs/rendering) (`render: "isg"` with `timeRevalidate`) is a per-route rendering mode. This port instead uses `src/lib/catalog-cache.ts` with the same host-aware strategy.
- **Waku** — first-party via plugin: Waku keeps caching out of core by design, and its own guides document the separate [`waku-cache`](https://waku.gg/guides/explicit-caching) package. This port does not use it; `optimized` hand-writes `src/lib/catalog-cache.ts` plus `middleware/html-cache-control.ts`, and `main` has neither.
- **Ember** — manual on `optimized`: `server/catalog-cache.js` plus `public/_headers`; `main` has neither. FastBoot provides SSR, not a data cache ([FastBoot](https://github.com/ember-fastboot/fastboot)).

The Cloudflare results in the 1.7–2.0 band are the ones to watch here. A cache that lives in isolate memory looks fine on Vercel and misses on Workers. Persistent KV/Blobs/Cache-API storage is what moves that row to 1.1–1.5.

### 5. Route prefetching

**Summary:** Next, Nuxt, and Pracht prefetch by default; SvelteKit, SolidStart, and TanStack Start expose first-party router primitives you turn on. Waku's helpers are still named `unstable_`. Ember's `<LinkTo>` has no prefetch behavior at all.

- **Next** — [`partialPrefetching`](https://nextjs.org/docs/app/api-reference/config/next-config-js/partialPrefetching), `prefetch={true}` on high-value links ([`<Link>`](https://nextjs.org/docs/app/api-reference/components/link)), and the `FastLink` pointer-down navigation.
- **Nuxt** — [`<NuxtLink>`](https://nuxt.com/docs/4.x/api/components/nuxt-link) `prefetch-on="visibility" | "interaction"`, `_payload.json` payload prefetch, and `prefetchPreloadTags`.
- **SvelteKit** — first-party: [`data-sveltekit-preload-data="hover"`](https://svelte.dev/docs/kit/link-options) plus explicit `preload` props on the pagination and sidebar.
- **SolidStart** — first-party: the router exposes [`usePreloadRoute`](https://docs.solidjs.com/solid-router/reference/preload-functions/preload); `FastLink` wires it to hover, focus, and pointer-down. There is no shared-shell partial prefetch.
- **TanStack Start** — first-party: the router supports [`preload`](https://tanstack.com/router/latest/docs/guide/preloading) with `intent` / `viewport`; this port sets `defaultPreload: 'intent'` in `src/router.tsx` and wraps links with `FastLink`.
- **Pracht** — built-in [`prefetch`](https://pracht.resynapse.dev/docs/prefetching) with `viewport` / `intent`.
- **Waku** — [`unstable_prefetchOnView` / `unstable_prefetchOnEnter`](https://waku.gg/guides/navigation-prefetching) on `FastLink`; still marked unstable in the API name, hence 🧪.
- **Ember** — manual: [`<LinkTo>`](https://api.emberjs.com/ember/release/classes/ember.templates.helpers/?anchor=link-to) has no prefetch behavior; this must be added with a custom modifier or service.

Prefetching barely moves Lighthouse FCP because it mostly helps the *next* navigation, not the first paint. It matters for how fast the app feels once someone starts clicking, which is the caveat in the companion [FCP analysis](./fcp-groupings.md#caveats).

**Summary:** Next has a strong FCP path but is not the broadest framework here. Nuxt has the widest set: per-route rules, art-direction components, first-party reactivity, script helpers, and Nitro presets, plus islands and an analyzer that are still experimental. Pracht is the only framework where islands are a stable per-route hydration mode, and it also has server islands, ISG, an analyzer, Preact signals, and first-party adapters. SvelteKit and SolidStart sit in the middle: strong routing and deploy primitives, but no islands and no first-party script or analysis tooling. Waku gets per-route rendering, adapters, and lazy slices, but its React runtime needs a third-party library for fine-grained reactivity. Ember has autotracking but little of the rest.

The honest reading is that **Next's advantage is depth on the FCP path, not breadth**. It has the best first-paint lever coverage, and it also has the strongest server-rendering story — React Server Components, Cache Components/PPR, and cache tags — which this table does not try to score. It trails on islands, art-direction ergonomics, per-route render policy under Cache Components, and first-party deploy adapters.

### 6. Partial hydration and islands

**Summary:** Pracht is the only framework that makes islands a stable per-route hydration mode. Nuxt ships them as experimental server components and `<NuxtIsland>`. Every other framework hydrates the whole client tree (🔧 — no package path either).

- **Next** — none. Server Components keep a component's JavaScript out of the browser, but every client component still hydrates as one tree. Cache Components splits static and request-time HTML, not hydration ([server and client components](https://nextjs.org/docs/app/getting-started/server-and-client-components)).
- **Nuxt** — experimental: [server components and islands](https://nuxt.com/docs/4.x/guide/concepts/server-components) render a component with no client JS; prop changes refetch the island ([`<NuxtIsland>`](https://nuxt.com/docs/4.x/api/components/nuxt-island)). Some features, such as slots, only work in single-file components.
- **SvelteKit** — none; all interactive components hydrate.
- **SolidStart** — none.
- **TanStack Start** — none.
- **Pracht** — first-class: `hydration: "islands"` per route, with interactive components discovered from `src/islands/`; `hydration: "none"` gives a zero-JS page ([islands](https://pracht.resynapse.dev/docs/islands)). This port does not set it, so it uses full hydration.
- **Waku** — none. Lazy slices cover server islands, not partial hydration.
- **Ember** — none.

### 7. Server islands and lazy slices

**Summary:** Pracht has a named server-island primitive and Waku has lazy slices. Next's Cache Components solves the same problem with a stable first-party flag, though not as a named island. Nuxt's `<NuxtIsland>` is still experimental. SvelteKit, SolidStart, TanStack Start, and Ember have no equivalent.

- **Next** — [`cacheComponents: true`](https://nextjs.org/docs/app/api-reference/config/next-config-js/cacheComponents), enabled here, renders a cached shell and fills request-time holes. That is functionally close to a server island, but the API is an uncached data boundary inside Suspense, not a named island with its own cache entry.
- **Nuxt** — [`<NuxtIsland>`](https://nuxt.com/docs/4.x/api/components/nuxt-island); props travel as query parameters so island responses can be cached by a CDN.
- **SvelteKit** — none.
- **SolidStart** — none.
- **TanStack Start** — none.
- **Pracht** — first-class [`server islands`](https://pracht.resynapse.dev/docs/server-islands): a fragment renders per request with cookies and middleware context while the surrounding page stays SSG/ISG.
- **Waku** — [`lazy slices`](https://waku.gg/#lazy-slices) are documented as similar to Astro's server islands.
- **Ember** — none.

### 8. Per-route render modes

**Summary:** Nuxt, SvelteKit, Pracht, and Waku let you pick static, cached, SSR, or SPA behaviour per route. SolidStart and TanStack Start have first-party per-route prerender/ISR, though not a full SSR/SPA switch. Next has no single switch, and with Cache Components its segment exports are removed in favour of `'use cache'` boundaries. Ember has no per-route switch.

- **Next** — route segment exports such as `dynamic` and `revalidate` exist, but with Cache Components enabled — as in this repo — they are removed in favour of `'use cache'` boundaries ([route segment config](https://nextjs.org/docs/app/api-reference/file-conventions/route-segment-config)). There is no single per-route `render:` switch.
- **Nuxt** — [`routeRules`](https://nuxt.com/docs/4.x/api/utils/define-route-rules): globs map to `prerender`, `swr`, `isr`, `ssr: false`, cache headers, redirects, and proxy rules. This port uses it for the catalog routes.
- **SvelteKit** — `export const prerender`, `ssr`, and `csr` per route ([page options](https://svelte.dev/docs/kit/page-options)).
- **SolidStart** — [route prerendering](https://docs.solidjs.com/solid-start/v1/building-your-application/route-prerendering) is configurable per route, but there is no per-route SSR/SPA switch.
- **TanStack Start** — [ISR](https://tanstack.com/start/latest/docs/framework/react/guide/isr) and static prerendering are per-route.
- **Pracht** — `render: "ssg" | "ssr" | "isg" | "spa"` per route in `src/routes.ts` ([rendering modes](https://pracht.resynapse.dev/docs/rendering)). Both routes in this port use `isg`.
- **Waku** — `render: 'static' | 'dynamic'` per page, layout, or slice ([rendering](https://waku.gg/#rendering)).
- **Ember** — SSR is a global FastBoot setting; there is no per-route render mode.

### 9. Art-directed images

**Summary:** Nuxt and SvelteKit ship a component or element that emits a `<picture>` with modern formats and fallbacks. Next supports art direction through `getImageProps()` but leaves the markup to you. SolidStart and TanStack Start pass URLs through Unpic and assemble the markup themselves; Pracht emits `srcset`/`sizes` but no `<picture>`. Waku and Ember have nothing.

- **Next** — [`getImageProps()`](https://nextjs.org/docs/app/api-reference/components/image#art-direction) returns per-breakpoint props; you hand-write the `<picture>` and `<source>` elements.
- **Nuxt** — [`<NuxtPicture>`](https://image.nuxt.com/usage/nuxt-picture) is a drop-in `<picture>` replacement that serves modern formats with a fallback, via `@nuxt/image`.
- **SvelteKit** — [`enhanced:img`](https://svelte.dev/docs/kit/images) is replaced at build time by an `<img>` wrapped in a `<picture>` with multiple types and sizes.
- **SolidStart** — [Unpic](https://unpic.pics) transforms URLs; the app assembles any `<picture>` markup itself.
- **TanStack Start** — same Unpic setup as SolidStart.
- **Pracht** — [`@pracht/image`](https://pracht.resynapse.dev/docs/images) emits `srcset`/`sizes` and reserves layout space, but there is no `<picture>` component.
- **Waku** — plain `<img>`, no `srcset`; the app would have to build it.
- **Ember** — plain `<img>`.

### 10. Fine-grained client reactivity

**Summary:** Vue, Svelte, Solid, and Ember track dependencies at the value level. Pracht gets the same from Preact's official signals package. The React-based ports re-render component subtrees; React Compiler memoizes work but does not change the model, so value-level reactivity needs a third-party signals library such as [`@preact/signals-react`](https://github.com/preactjs/signals) (🧪).

- **Next** — React. [`reactCompiler: true`](https://react.dev/learn/react-compiler) is enabled in this repo and auto-memoizes, but state updates still re-render component subtrees.
- **Nuxt** — Vue's [`ref`/`reactive`](https://vuejs.org/guide/essentials/reactivity-fundamentals) tracks dependencies and updates the affected effects.
- **SvelteKit** — [runes](https://svelte.dev/docs/svelte/what-are-runes) with compile-time dependency tracking.
- **SolidStart** — [signals](https://docs.solidjs.com/concepts/signals); updates write to the DOM directly without re-running components.
- **TanStack Start** — follows the variant: React here, [Solid](https://docs.solidjs.com/concepts/signals) in `tanstack-solid-books`.
- **Pracht** — Preact; [signals](https://preactjs.com/guide/v10/signals/) are an official package from the Preact team.
- **Waku** — React, with no compiler enabled by default.
- **Ember** — [`@tracked` autotracking](https://guides.emberjs.com/release/in-depth-topics/autotracking-in-depth/).

This is an interaction-cost property, not a first-paint one. It shows up in INP and memory on long-lived pages, not in the FCP bands.

### 11. Bundle analysis

**Summary:** Next and Pracht ship a stable analyzer command; Nuxt's is marked experimental. The remaining Vite ports use the community `rollup-plugin-visualizer`, and Ember uses a community addon.

- **Next** — [`next analyze`](https://nextjs.org/docs/app/guides/package-bundling) (v16.1+) opens the Turbopack module graph with per-route client/server filtering; `--output` saves a static report and `next analyze export` (v16.4+) streams the saved data. The same guide covers the `@next/bundle-analyzer` plugin for webpack builds.
- **Nuxt** — [`nuxt analyze`](https://nuxt.com/docs/4.x/api/commands/analyze) (experimental) builds the app and serves client and Nitro reports; `--json` writes machine-readable output.
- **SvelteKit** — [rollup-plugin-visualizer](https://github.com/btd/rollup-plugin-visualizer) in `vite.config.ts`.
- **SolidStart** — the same Vite plugin.
- **TanStack Start** — the same Vite plugin.
- **Pracht** — [`pracht build --analyze`](https://pracht.resynapse.dev/docs/performance) prints per-route gzip and raw sizes; `--json` for scripts.
- **Waku** — the same Vite plugin.
- **Ember** — [ember-cli-bundle-analyzer](https://github.com/simonihmig/ember-cli-bundle-analyzer) addon.

### 12. Third-party script strategies

**Summary:** Next and Nuxt have first-party script components with loading strategies and proxying. Everything else leaves ordering and deferral to the app.

- **Next** — [`next/script`](https://nextjs.org/docs/app/api-reference/components/script) with `beforeInteractive`, `afterInteractive`, `lazyOnload`, and `worker` (Partytown) strategies.
- **Nuxt** — [`@nuxt/scripts`](https://scripts.nuxt.com/) with per-script strategy, proxying, and Partytown support.
- **SvelteKit** — no framework primitive; add the tag in `app.html` or a component and manage ordering yourself.
- **SolidStart** — manual.
- **TanStack Start** — manual; the router's `Scripts` component handles router scripts, not third-party strategy.
- **Pracht** — manual.
- **Waku** — manual.
- **Ember** — manual; a script tag in `index.html` or an addon.

### 13. Portable multi-host deployment

**Summary:** Nuxt, SolidStart, and TanStack Start use Nitro presets; SvelteKit, Pracht, and Waku ship first-party adapters. All cover Node, Vercel, Netlify, and Cloudflare. Next relies on `output: 'standalone'` plus the community OpenNext adapters (🧪). Ember has no equivalent. That gap is why host-specific caching is hand-written in the FCP analysis.

- **Next** — [`output: 'standalone'`](https://nextjs.org/docs/app/api-reference/config/next-config-js/output) plus [OpenNext](https://opennext.js.org/) adapters for Cloudflare, Netlify, and AWS; both are outside core.
- **Nuxt** — Nitro [`presets`](https://nitro.build/deploy) cover every host in this benchmark.
- **SvelteKit** — first-party [`adapters`](https://svelte.dev/docs/kit/adapters) for Node, Vercel, Netlify, Cloudflare, and static output.
- **SolidStart** — Nitro presets ([deploying your app](https://docs.solidjs.com/guides/deploying-your-app)).
- **TanStack Start** — Nitro and partner plugins ([hosting](https://tanstack.com/start/latest/docs/framework/react/guide/hosting)).
- **Pracht** — first-party [`adapters`](https://pracht.resynapse.dev/docs/adapters) for Node, Vercel, Netlify, and Cloudflare.
- **Waku** — first-party [`adapters`](https://waku.gg/#deployment) for Node, Vercel, Netlify, Cloudflare, and Deno (experimental).
- **Ember** — FastBoot plus Embroider; no first-party host adapters.

Read the two tables together, and treat the combined score as a rough capability count. A framework can have more of these features and still land in a slower FCP band — Pracht has islands, ISR, adapters, and an analyzer, and still measures 1.2–1.5s. The first table explains the bands; this one explains what each framework can do once the page is loaded.
